Storage Both docs

Base platform storage (Munshi)

  • IBM Storage Fusion operator installed to namespace ibm-spectrum-fusion-ns, update channel v2.0, Manual approval (Automatic not supported by IBM Fusion).
  • IBM Operator Catalog added via CatalogSource ibm-operator-catalog in openshift-marketplace, image icr.io/cpopen/ibm-operator-catalog:latest, poll interval 45m.
  • IBM Storage Fusion Data Foundation (FDF) installed on top, providing the Ceph-based OpenShift Data Foundation (ODF) layer — device type: Local.
  • Local Storage Operator (namespace openshift-local-storage) provisions two LocalVolumeSets:
    • infra-mon-lvs → storageClass infra-mon-sc, Filesystem/xfs, 50G–550G, max 6 devices (monitoring/logging)
    • infra-fdf-lvs → storageClass infra-fdf-sc, Block, 7T–8T, max 3 devices (FDF/ODF)
  • Registry storage: S3-compatible OBC (registry-obc) in openshift-image-registry, registry scaled to 2 replicas.

MaaS-layer storage usage (Sid)

  • IBM Storage Fusion integrated via ODF provides S3-equivalent object storage and block storage (PVC) to the MaaS layer.
  • Object storage (S3): hosts foundational LLM model weights; LLMInferenceService pulls weights from ODF-backed S3 endpoint at pod init.
  • Block storage (PVC): backs the single PostgreSQL instance (namespace postgresql), which is the shared relational backend for Keycloak, maas-api, and the Model Registry.

Authentication Posture — Infra Layer Munshi's CER

At the time of this report, TNB's cluster used local HTPasswd only as the active identity provider. LDAP/AD integration is documented as a reference in the report but was not yet configured — the doc explicitly warns HTPasswd should only be used for production temporarily / dev environments, not long-term.
  • HTPasswd secret: htpasswd-secret-aidc, IdP display name "Identity Providers (Local)".
  • Reference-only LDAP config shown in the doc for a future "Identity Provider (TNB AD)":
    • Bind DN: CN=srv.aidc,OU=ServiceAccount,DC=tnb,DC=my
    • URL: ldaps://tnbhqsvrdc01.tnb.my:636/DC=tnb,DC=my?sAMAccountName?sub?(objectClass=user)
    • Bind password secret: tnb-ad-ldap-bind-secret · CA secret: tnb-ad-ldap-ca-cert
    • Attribute mapping: email→mail, id→dn, name→cn, preferredUsername→sAMAccountName
  • RBAC reference group: OCPUAT-CLUSTER-ADM mapped to cluster-admin via oc adm policy add-cluster-role-to-group.
  • Hardening steps documented: delete kubeadmin secret post-IdP setup; remove self-provisioner role from system:authenticated:oauth group to stop users from freely creating projects.
  • Custom KubeletConfig (master-custom-kubelet-config): maxPods: 2000, systemReserved cpu 2.35 / memory 17Gi, TLS cipher suites restricted to AES-GCM ECDHE suites, eviction thresholds tuned (hard/soft).
Important nuance: this HTPasswd-only posture is the base OCP cluster's auth story. The MaaS/RHOAI layer (Sid's report) later layers Keycloak federated to Active Directory over LDAPS on top as the real IdP for the RHOAI dashboard and OpenShift OAuth — see "MaaS Identity" section below. These are two different points in time / two different reports.

MaaS / RHOAI Platform Architecture Sid's CER

Built on top of the OCP 4.20 base cluster above. Focus: Model-as-a-Service for LLM inference with governed, multi-tenant API access.

Operator ecosystem

Red Hat OpenShift AI (RHOAI) v3.4 Kuadrant (Connectivity Link) Authorino OpenShift Service Mesh NVIDIA GPU Operator Node Feature Discovery Red Hat Build of Keycloak (RHBK) Grafana Operator

Layered logical architecture (6 layers)

  1. Client/consumer — application teams / chatbots sending OpenAI-compatible REST API requests.
  2. Routing/ingress & governance — Kuadrant (Red Hat Connectivity Link) API Gateway enforcing AuthPolicy (API Keys) and RateLimitPolicy (RPM/TPM).
  3. Model orchestration — KServe manages serving lifecycle, autoscaling, request concurrency.
  4. Model serving — vLLM ServingRuntime pods, Tensor Parallelism across GPUs.
  5. Persistence & observability — S3 object storage for weights; Prometheus scraping vLLM metrics.
  6. Infrastructure — OpenShift worker nodes with NVIDIA GPUs + NVIDIA GPU Operator.

End-to-end traffic flow

MetalLB LoadBalancer (on-prem, fixed IP pool) → TLS termination at the Gateway in openshift-ingress (hostname maas.apps.aidc.tnb.com.my, ports 80/443, cert via cert-manager-ingress-cert) → Kuadrant policy enforcement (Authorino auth check + Limitador rate-limit check) → routed to maas-api in models-as-a-service → forwards to the actual model-serving pods in llm namespace.
  • Hardware targeting: NFD + NVIDIA GPU Operator label nodes by hardware; RHOAI Hardware Profiles route heavy workloads (e.g. GPT-OSS-20B) to the two H200 nodes, lighter workloads (e.g. Qwen2.5-7B) to the RTX 6000 Pro node.
  • Gateway API object: gateway.networking.k8s.io/v1 Gateway named maas-default-gateway, gatewayClassName openshift-default, listener on port 443 (HTTPS) allowing routes from all namespaces, TLS mode Terminate. Annotated opendatahub.io/managed: 'false' and security.opendatahub.io/authorino-tls-bootstrap: 'true'.

Kuadrant & Authorino

  • Kuadrant CR named kuadrant in kuadrant-system.
  • Limitador configured with RateLimitPolicy on the Gateway — limits by Requests-Per-Minute (RPM) and Tokens-Per-Minute (TPM).
  • Authorino instance authorino, clusterWide: true, TLS via secret authorino-server-cert for both external listener and internal OIDC server.
  • AuthPolicy directs Authorino to call the internal maas-api validation endpoint to check API keys sent in the HTTP Authorization header — if valid, traffic proceeds to the model serving namespace.

MaaS Identity — Keycloak / AD Federation Sid's CER

  • Red Hat Build of Keycloak (RHBK) deployed in namespace keycloak; 1 instance, HTTPS port 8443, TLS secret keycloak-internal-tls.
  • Database: dedicated PostgreSQL instance (namespace postgresql), PVCs backed by IBM Storage Fusion/ODF. DB secret keycloak-db-secret — database name keycloak, host postgresql.postgresql.svc.cluster.local, port 5432, username sso-admin.
  • Active Directory federation over LDAPS: a Keycloak Realm + User Federation provider syncs users directly from corporate AD.
  • Group mappings: LDAP Group Mappers translate AD groups into OpenShift roles — e.g. an AD AI-Admins group maps to cluster-admin / RHOAI admin roles.
  • OpenShift OAuth integration: an OIDC client (openshift-oauth) is created in Keycloak; OpenShift's global OAuth CR is updated to use Keycloak as an OpenID identity provider — issuer https://sso.apps.aidc.tnb.com.my/realms/openshift, client secret keycloak-oauth-client-secret, claims mapped for email/groups/name/preferredUsername.
  • Because RHOAI inherits auth from OpenShift Auth, Keycloak implicitly secures the RHOAI dashboard and workbench access.
  • Custom TNB Keycloak theme: tnb-keycloak-theme.jar, mounted via configmap tnb-theme into the Keycloak pod template.
  • Important distinction: Kuadrant (the API Gateway for inference traffic) does NOT integrate directly with Keycloak — inference API auth is handled separately via API Keys + maas-api validation, not SSO/OIDC. Keycloak secures human/dashboard access; Kuadrant/Authorino secures machine/API traffic.

Quality of Service Strategy Sid's CER

High Availability

Achieved via Knative autoscaling + pod anti-affinity. When traffic scales an InferenceService to multiple replicas, anti-affinity rules spread pods across GPU-enabled physical hosts, protecting against single-node failure.

Failover

If an inference pod crashes (e.g. CUDA OOM), the KServe controller auto-provisions a replacement. Client traffic is briefly queued by the Knative Activator until the new pod finishes downloading the model and becomes Ready.

Architectural Records — Policies, Principles & ADRs Sid's CER

POLICY-001 — Centralized Identity Management

All users/admin access must authenticate through corporate AD; local accounts must not be used for production platform access. Source: TNB IAM standards. Related: ADR-004, "Use Keycloak as Centralized IAM Broker."

POLICY-002 — On-Premises Data Sovereignty

Foundational models, training weights, and user prompt payloads must remain entirely on-prem. Cloud-based LLM APIs cannot be used. Related: baremetal compact cluster + IBM Storage Fusion (ODF) integration.

PRINCIPLE-001 — Decoupled Governance from Model Serving

vLLM must be dedicated entirely to inferencing; auth/authz/rate-limiting must be fully decoupled and handled at the edge (Gateway layer). Motivation: consistent security/billing governance regardless of model/runtime. Related: ADR-002, "Use Kuadrant for API Governance."

PRINCIPLE-002 — Hardware-Aware Workload Scheduling

AI workloads must be explicitly targeted to physical nodes via RHOAI hardware profiles/node selectors to differentiate H200 vs. RTX 6000 Pro tiers. Motivation: prevent resource contention, ensure heavy models land on the strongest GPUs.

ADR-001 — Selection of vLLM as Serving Runtime

Decision: use vLLM for all LLM InferenceServices. Justification: PagedAttention minimizes GPU memory fragmentation; continuous batching boosts throughput. No formal alternatives evaluated.

ADR-002 — Use Kuadrant for API Governance

Decision: deploy Kuadrant (RHCL) + Authorino + Limitador rather than a standalone NGINX ingress or third-party gateway (e.g. Kong). Justification: natively supported within the OpenShift MaaS architecture; integrates seamlessly with the maas-api control plane.

Next Steps, Training & Knowledge Transfer Sid's CER

Technical next steps

MIG — Multi-Instance GPU

A single H200 can be securely partitioned into up to 7 isolated GPU instances, letting the platform serve multiple smaller models concurrently on one card (huge density/ROI gain). Note: RTX 6000 Pro does NOT support MIG — this optimization targets only the data-center-class H200 nodes.

Kueue — Job Queuing & Quotas

Currently kueue is Removed in the DSC. Recommended addition to manage job queuing/resource quotas for async batch, training, and fine-tuning workloads across tenants, plus "Fair Share" quotas so no single team monopolizes GPU capacity.
